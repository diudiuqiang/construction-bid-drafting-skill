# 二次修正流程

## 0. 什么时候触发二次修正

初稿是「基于现有资料」的稿。出现以下任一情况，就要做二次修正：

1. **设计图纸到位**——原挂〔初稿注〕的组件型号、支架形式、基础做法需要落定；
2. **勘察报告到位**——地质、水文、鱼塘水深等终值需要替换估计值；
3. **业主/设计补充资料**——疑问答复、现场条件变更；
4. **评审反馈**——专家提出的修改意见；
5. **清单更新**——禁用词表、硬指标表、规范清单有变动。

## 1. 基线机制（核心）

每次体检都会输出 JSON，其中 `fingerprint` 是问题指纹集合：

```
格式：类别|类型|详情
示例：A|禁用词|长丰（2 处）
     B|缺表名表格|L1161 施工机械配置表
     C|AI痕迹|高置信 AI 套话 3 处: ...
```

**每次体检后，把本次 JSON 存为下次的基线**：

```
out/compliance.json  →  复制为  out/compliance_prev.json
```

下次体检传 `--prev ./out/compliance_prev.json`，自动输出三类变化：

| 变化 | 含义 | 处理 |
|---|---|---|
| 新增 | 上次没有、这次出现 | 重点查：是改出来的新问题，还是基线没覆盖 |
| 已修复 | 上次有、这次没有 | 确认修复方式正确，别改反弹 |
| 遗留 | 两次都有 | 老问题，要么处理要么明确接受 |

指纹是**精确字符串比对**：同一问题只要表述略有变化（比如行号变了），就会被判成
「新增 + 已修复」两条。所以看完变化表要人工复核，别被数字吓到。

## 2. 二次修正的标准流程

### 第一步：锁定基线

```bash
cp out/compliance.json out/compliance_prev.json
```

**不要删旧的 prev**——没有基线就无法判断「新增 vs 遗留」。

### 第二步：吸收新资料

把新资料里的关键信息落到对应位置：

| 资料类型 | 落点 |
|---|---|
| 设计图纸 | 组件型号/数量、支架形式、基础做法、总平面布置 |
| 勘察报告 | 地质剖面、承载力、地下水位、鱼塘水深 |
| 疑问答复 | 对应章节的〔初稿注〕处 |
| 现场条件变更 | 写作基准 第 2 节「现场事实」表 |

### 第三步：替换〔初稿注〕

每个〔初稿注〕对应一个待定项。资料到位后：

1. 删掉〔初稿注〕；
2. 写入确定值；
3. 检查该值是否影响其他章节（组件型号变了，采购章节、资源配置、总平面都要联动）。

**注意**：全篇〔初稿注〕上限 10 处（见《合规红线与硬指标.md》）。
替换后如果还有新的待定项，要先把已解决的注释放上，再挂新注——**总数不能超**。

### 第四步：更新配置

- 新规范 → 加到 conf/规范清单；
- 新禁用词 → 加到 conf/禁用词.txt；
- 新硬指标 → 加到 conf/硬指标.txt；
- 新跨册引用 → 加到 conf/cross_ref.json。

### 第五步：重跑体检 + 基线对比

```bash
python compliance_check.py --in ./out/施工方案.md \
    --banned ./conf/禁用词.txt --hard ./conf/硬指标.txt \
    --prev ./out/compliance_prev.json \
    --report ./out/compliance.json --md ./out/合规体检报告.md
```

重点看「新增 / 已修复 / 遗留」三张表：

- **新增** = 二次修正引入的问题，必须清零；
- **已修复** = 确认修对了；
- **遗留** = 决定是否本轮处理。

### 第六步：归档

```
out/
├── compliance_prev.json   ← 上次基线（保留）
├── compliance.json        ← 本次结果（下次的基线）
└── 合规体检报告.md         ← 人读版
```

## 3. 二次修正的铁律

1. **不重写全文**——只改受新资料影响的部分，避免把已经合规的内容改坏。
2. **不动基线**——`compliance_prev.json` 一旦生成就不改，它是对比的锚。
3. **新增问题清零**——二次修正后「新增」必须为 0，否则说明修正引入了新问题。
4. **联动检查**——改一个参数，全文搜一遍相关表述（型号、数量、工期、人数）。
5. **初稿注只减不增**——资料每到位一批，注就该少一批；新增注要有充分理由。

## 4. 与设计/勘察资料的接口

| 资料里的字段 | 正文落点 | 常见坑 |
|---|---|---|
| 组件型号/功率 | 3.1 施工部署、4 采购 | 型号变了但表格没改 |
| 支架形式（固定/可调） | 3.2 重难点方案 | 可调支架要重算工时 |
| 基础形式（螺旋桩/混凝土） | 3.2、3.3 资源配置 | **本项目禁用钻孔灌注桩** |
| 总平面布置图 | 3.1 施工部署 | 与现场事实 A 组矛盾 |
| 地质承载力 | 3.2 基础方案 | 估计值→终值要联动机械配置 |
| 鱼塘水深/底质 | 3.2 水上作业 | 影响作业方式与工效 |
| 并网接入方案 | 3.1、8 保修 | 影响调试与验收章节 |

## 5. 二次修正后的交付检查

- [ ] A 类问题 = 0
- [ ] 「新增」问题 = 0
- [ ] 〔初稿注〕数量 ≤ 上限，且每处都有明确来源待补
- [ ] 表格编号连续、无缺号
- [ ] docx 元数据无工具痕迹（`--verify` 通过）
- [ ] 含图片时已跑视觉终检（见 `Word图表混排与视觉终检.md`）
- [ ] 基线 JSON 已归档

### 5.1 多交付件同源（容易漏）

一份技术标往往不止一个文件：正文 Word / Markdown、施工进度计划 Excel、
《初稿编制说明与待修正清单》、有时还有单独的平面图或附表。
**口径变更必须四件联动**，只改正文会造成评审手里的两份材料互相打架。

实测踩过的情形：发包人澄清「勘察设计与施工准备并行、第 16 天正式施工、施工工期 120 天」
之后，Excel 进度计划已按新口径重排，正文里的机械表、劳动力表、关键线路一览表却仍是旧数；
Excel 的构建脚本里还留着旧的现场分块表述。直到把正文与 Excel 逐项对齐才收口。

做法：

1. **列一张同源清单**：把「同一个数字出现在哪几个文件的哪几张表」写下来
   （工期节点、里程碑、关键线路、工种人数峰值、机械台套数、场地分块、组件数量等最常串）。
2. **改一份就全表扫一遍**：`grep` 旧值，确认四个交付件里都没有残留。
3. **派生表也要纳入基线**：Excel 是正文派生出来的，正文改了它就得重建；
   重建后跑公式重算，确认 0 错误。
4. **清单留痕**：在《待修正清单》里注明本轮口径变更影响了哪几件交付物。
5. **交付前交叉核对**：把 Excel 各工作表的主要数字与正文对应表逐行比对一次。

> 把 Excel 各工作表拆进 Word 时，表下注明「本表与《XXX.xlsx》「YYY」工作表口径一致」，
> 既是给评委看的溯源，也提醒自己这两处必须同步。

## 6. 多轮修正的基线滚动

```
第 1 轮：compliance.json（基线 A）
第 2 轮：compliance_prev.json = A，产出 compliance.json（基线 B）
第 3 轮：compliance_prev.json = B，产出 compliance.json（基线 C）
```

每轮只与**上一轮**比，不要跨轮比——跨轮比会把中间已修复的问题误判为「新增」。

若中途换了禁用词表/硬指标表（配置变更），应**另起基线**，并在报告里注明配置版本，
否则指纹变化无法归因。
