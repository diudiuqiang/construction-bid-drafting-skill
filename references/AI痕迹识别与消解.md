# AI 痕迹识别与消解

## 0. 目标

不是「消灭一切 AI 味」，而是**消除高置信度的模板化痕迹**，让正文读起来像人写的工程文本。

两条底线：

1. HIGH_AI / CLICHE 词表命中 = 必须改（bad 级）；
2. docx 元数据不得出现工具名 / AI 名。

C 类（warn 级）在草稿阶段可接受，提交前应处理。

## 1. 检测维度与阈值

### 1.1 套话词频

**HIGH_AI（36 条，命中即 bad）**：

> 综上所述 / 由此可见 / 毋庸置疑 / 不言而喻 / 众所周知 / 值得注意的是 / 需要指出的是 /
> 不难看出 / 毫无疑问 / 在一定程度上 / 总的来说 / 总体而言 / 综合来看 / 综合以上 /
> 在这个过程中 / 在这个背景下 / 让我们 / 首先，我们需要 / 首先，我们 / 在当今 / 在当今社会 /
> 随着社会的不断发展 / 日益增长 / 具有重要意义 / 发挥了重要作用 / 取得了显著成效 /
> 奠定了坚实基础 / 提供了有力保障 / 注入新的活力 / 增添了新的动能 / 擘画 / 赋能 / 聚焦 /
> 凝心聚力 / 砥砺前行 / 奋进 / 新时代 / 新征程 / 高质量发展

**MID_AI（24 条，合计 >5 处 warn）**：

> 一方面 / 另一方面 / 不仅 / 而且 / 既 / 又 / 从而 / 进而 / 同时 / 因此 / 所以 / 为此 /
> 基于此 / 在此基础上 / 与此同时 / 此外 / 另外 / 首先 / 其次 / 最后 / 综上 / 简言之 /
> 换言之 / 换句话说

> **「既」的误判已修**：工程文本里「既有线路 / 既有分界 / 既有电杆」是合法用语，
> 脚本先剔除 `既有` 再统计 `既`，剩下的才是 `既…又…` 平行结构。
> 不做这层剔除，一份 16 万字的正规施组会被误报 100+ 处。

**CLICHE（11 条，命中即 bad）**：

> 具有重要意义 / 发挥了重要作用 / 取得了显著成效 / 奠定了坚实基础 / 提供了有力保障 /
> 注入了新的活力 / 增添了新的动能 / 提供了新思路 / 具有重要意义和深远影响 /
> 发挥了积极作用 / 取得了良好效果

### 1.2 段落长度分布

只统计正文段落（剔除标题、表格行、列表行），不足 5 段不判断。

| 变异系数 CV | 级别 | 含义 |
|---|---|---|
| < 0.25 | bad | 段长过于均匀，疑似模板化 |
| 0.25 ~ 0.35 | warn | 略均匀 |
| ≥ 0.35 | ok | 正常 |

### 1.3 句子长度分布

按 `。！？；` 切句，不足 10 句不判断。

| CV | 级别 |
|---|---|
| < 0.30 | bad |
| 0.30 ~ 0.40 | warn |
| ≥ 0.40 | ok |

### 1.4 标点习惯

| 检查项 | 判据 | 级别 |
|---|---|---|
| 半角标点混入中文（`中,中` `中.中` `中;中` `中:中`） | >5 处 bad，1–5 处 warn | bad/warn |
| 破折号 `——` 密度 | >8/千字 bad，>4/千字 warn | bad/warn |
| 感叹号 `！` | 任意 | bad |
| 连续标点（`，，`/`。。`） | 任意 | 提示 |

### 1.5 标题对仗

同一级标题结尾 2 字相同的比例（该级标题 ≥4 个才判断）：

| 比例 | 级别 |
|---|---|
| ≥ 0.7 | bad（疑似模板化对仗） |
| ≥ 0.5 | warn |

### 1.6 句首重复

同一 2 字开头的句子占比（≥10 句才判断）：

| 比例 | 级别 |
|---|---|
| > 0.35 | bad |
| > 0.25 | warn |

## 2. 评分与分级

```
score = max(0, 100 - 25 × bad数 - 10 × warn数)
level = bad（有 bad）/ warn（仅 warn）/ ok
```

体检脚本把 bad 级 AI 问题归入 **A 类**（红线），warn 级归入 **C 类**（建议优化）。

## 3. 消解方法

### 3.1 元数据层（必须做）

| 项 | 正确值 | 错误值 |
|---|---|---|
| docProps/app.xml `Application` | `Microsoft Office Word` | WorkBuddy / python-docx / 脚本名 |
| docProps/core.xml `creator` | 投标技术组（或真人名） | WorkBuddy / AI / Agent |

生成时传参：

```bash
python build_docx.py --in x.md --out x.docx --creator "投标技术组"
```

`--application` 默认已是 `Microsoft Office Word`，不要改。

### 3.2 内容层（逐条改）

1. **HIGH_AI / CLICHE 命中**：删掉或改写。
   - 「综上所述」→ 直接说结论，或删；
   - 「值得注意的是」→ 删；
   - 「在一定程度上」→ 删；
   - 「高质量发展」→ 换成具体动作。
2. **破折号密度高**：把 `——` 改成逗号、分号或拆句。
3. **半角标点**：全文替换 `,`→`，`、`.`→`。`、`;`→`；`、`:`→`：`
   （注意不要动英文、数字、规范编号里的半角）。
4. **段长过于均匀**：合并过短段落、拆分过长段落，制造自然起伏。
5. **句首重复**：同一连接词开头超过 1/4 时，把部分句子改成主语开头或合并。
6. **标题对仗**：同级标题结尾别都用同一词，换具体名词。

### 3.3 标点规范

- 中文正文一律全角：，。；：？！（）
- 数字、英文、规范编号用半角：GB 50204-2015、5.76MW、10kV
- 不用破折号做解释，用逗号或括号
- 工程文本不用感叹号

## 4. 自检命令

```bash
python compliance_check.py --in ./out/施工方案.md \
    --banned ./conf/禁用词.txt --hard ./conf/硬指标.txt \
    --report ./out/compliance.json --md ./out/合规体检报告.md
```

报告「AI 痕迹明细」给出每个维度的具体数值（段长均值/CV、句长均值/CV、标点计数等）。

## 5. 注意事项

- MID_AI 里「首先/其次/最后/此外/另外」在工程文本里是正常的，**只有密度过高才告警**（>5 处）。
  不要为了压低数字把它们全删，会把文章写得磕磕绊绊。
- 段落/句长 CV 是统计量，**受表格与列表影响**；正文不足 5 段 / 10 句时不判断，不要硬凑。
- 消解后必须重跑体检确认 score 上升，不要凭感觉。
- 表格内文字也计入统计，但表格本身就该规整——不要把表格内容当「段长均匀」的证据，
  应看正文段落。
- **合规要求的固定措辞不得为了降分而改写**。招标文件规定的章名、前附表要求的表述、
  硬指标要求重复出现的关键词（例如「关键线路」须双重出现），撞上「标题对仗」或「重复」
  类判据时，改**结构或判据**（见 `章号重构与合卷.md` 第 2 节坑三），不动措辞。
  技术标是合格制，改了规定措辞的风险远大于 AI 痕迹扣的那点印象分。
- **合法工程用语会被单字/词频误伤**：「既有线路 / 既有电杆 / 既有分界」里的「既」曾在
  16 万字正文里被报 117 处。统计前先剔除这类固定搭配，再数单字。
- 判据本身也会误报、会回归。改判据前先读 `校验器维护与误判边界.md`：
  重跑基线看「新增」、造正反例、外部审计逐条实测不照单全收。

## 6. 一句话判据

> 评审翻稿子时，如果某一页的每一段都差不多长、每个标题都同一个结尾、每句都从同一个词开头——
> 那就是 AI 痕迹。打散它。
