# 校验器维护与误判边界

## 0. 为什么单独立这一篇

`compliance_check.py` / `ai_trace.py` / `audit_structure.py` 也是代码。它们会：

- **误报**（把合法工程用语、招标规定措辞判成问题）；
- **漏报**（只看「有没有」，不看「出现几次」）；
- **回归**（修一个判据，造出一批新误报）。

更麻烦的是：体检报告是「要不要交付」的依据。**判据错了，全绿也是假的，报红也可能不该改**。
所以维护校验器本身要有规矩，不能凭报告数字直接动手改正文。

---

## 1. 第一原则（红线）

> **招标文件规定、评标口径要求、或决策记录里写死的措辞，不得为了降低 AI 痕迹评分而改写。**

典型冲突：招标文件规定四个章名里三个以「方案」结尾，`ai_trace.py` 的「同级标题结尾重复率」
判成模板化对仗（bad / warn）。**这时要改的是结构或判据，不是章名**——章名改了就可能构成偏差。

处理方式见 `章号重构与合卷.md` 第 2 节坑三：标题整体上移一级，让章级成为大纲顶层，
同级重复率自然下降；或者把「招标规定的固定章名」列入白名单跳过该项统计。
**绝不能**为了分数把「工程总承包管理方案」改成「工程总承包管理措施」。

同理，硬指标要求「关键线路」在正文**双重出现**、某尾水指标出现两次，这些重复是合规加分项，
不是 AI 痕迹，别顺手删掉。

---

## 2. 改判据的三条铁律

### 铁律一：重跑基线，看「新增」而不是只看总数

判据改动前后，用同一份稿件各跑一次体检，对比 `A/B/C/D/E` 各类计数。
**总数不变也可能藏着回归**：曾有一次修复让 B 类从 15 变 23，再修回 15——中间那 8 条全是新误报，
只盯最终数字会以为没事。

```bash
cp ./out/compliance.json ./out/compliance_prev.json
# 改判据…
python scripts/compliance_check.py --in ./out/施工方案.md \
    --prev ./out/compliance_prev.json \
    --report ./out/compliance.json --md ./out/合规体检报告.md
```

输出里「新增」必须为 0。

### 铁律二：必须造正反例

每个判据改动，至少准备**一个应当命中**的字符串和**一个不应当命中**的字符串，直接调函数验证：

```python
# 例：题注判据
assert is_caption('图 1-1 横道图（第 1~77 日历天，W1~W11）') is True   # 含全角逗号仍应命中
assert is_caption('表 1-1 按招标文件附表格式编制，列全拟投入设备。') is False  # 正文长句不得命中
```

「含全角逗号仍应命中」这条就是实测补上的：最初用「不含句读标点」判题注，结果所有带括号说明的图题全漏判。

### 铁律三：外部审计逐条实测，不照单全收

拿第三方审计报告当**待验证假设**，不是结论。一次实测的 8 条建议，结论是
**5 条完全正确、2 条部分正确、1 条建议被否**：

| 类型 | 处置 |
|---|---|
| 5 条完全正确 | 采纳，修脚本 |
| 2 条部分正确 | 只修属实的部分，保留对方建议删掉但确有引用的函数 |
| 1 条建议被否 | 「重复编号即报」会误伤 37 处合法跨册引用 → 改为「定义感知」的悬空引用检测 |

**被否的那条最值钱**：一个听起来很合理的检测规则，放到 16 万字真实文档里可能制造几十条假警报。
判据的代价要按「误报数」衡量，不按「听起来严不严格」衡量。

## 3. 已修过的误报案例（改判据前先对照）

| 现象 | 根因 | 修法 |
|---|---|---|
| 16 万字里报 117 处「既」AI 痕迹 | 单字匹配命中「既有线路 / 既有电杆 / 既有分界」等合法工程用语 | 先剔除 `既有` 再统计单字 `既` |
| 句首两字大量变成 `##` | 把 Markdown 标题行当句子送进统计 | 统计前用 `_body_text()` 剔除标题行 |
| 「标题结构不衔接」误报兄弟节点 | 用「上一级标题」判断父子，兄弟节点被当子节点 | 改**祖先追溯**，并只对带编号的祖先做判断 |
| 祖先全无编号时冒出 8 条「上层 None」 | `any([])` 为 `False`，空集合被当成「不衔接」 | 先过滤出带编号的祖先，空集合跳过 |
| 硬指标「双重出现」判据形同虚设 | 只判「有没有」，写一次也放过 | `parse_hard_rules()` 支持 `指标名: 关键字:N` 次数声明 |
| `--title-keywords` 永远不命中 | 文档示例里写占位符「项目名」，不是真实项目名 | 示例改真实项目名，并加「未发现 Title」提示（不判失败） |
| `--segments` 状态被误读为「册内编号也合格」 | 输出没说明状态覆盖范围 | 加 `status_scope` 字段 + `SKILL.md` 说明 |
| 「标题对仗」报招标规定章名 | 固定章名结尾重复 | 见第 1 节，改结构 / 白名单，不改措辞 |

**共同规律**：误报大多来自「用轻量启发式去判别需要语境的事」。判据越宽，越要配白名单、正反例和人工复核入口。

## 4. 配置变更要另起基线

`compliance.json` 的指纹依赖禁用词表、硬指标表、措辞归一表。
中途换了 `conf/` 里的任何一个，**不要**拿旧基线做对比——指纹变化无法归因，
会把「配置变了」误判成「正文新增了一堆问题」。

做法：另起基线，并在报告里注明配置版本。

多轮修正的基线**只与上一轮比**，不要跨轮比：

```
第 1 轮：compliance.json（基线 A）
第 2 轮：compliance_prev.json = A → compliance.json（基线 B）
第 3 轮：compliance_prev.json = B → compliance.json（基线 C）
```

## 5. 误报处置流程

1. **先复现**：拿到报告里的问题行号和原文，确认是正文真错了还是判据错了。
2. **查白名单 / 决策记录**：若该措辞是招标规定、硬指标、或决策记录写死的，判为误报，不动正文。
3. **判误报影响面**：同类字符串全文有多少处？若几十处，说明是判据问题，不是个例。
4. **改判据 + 造正反例 + 重跑基线**，确认「新增」为 0。
5. **留痕**：把案例写进本文件第 3 节表格，并在工作日志记一句根因。
6. **不要静默降阈值**：把 `warn` 阈值从 0.5 调到 0.9 让报告变绿，是自欺。
   若确需调，必须写明理由与适用范围。

- [ ] 合规固定措辞未被改写；若判据与之冲突，改的是判据或结构

- [ ] 新误报案例已回写本文件
- [ ] 全文重跑 `compliance_check` / `ai_trace` / `audit_structure` / `build_docx --verify`

## 7. 一句话判据

> 体检报告是证据，不是判决。先问「这条是正文错了，还是尺子歪了」——
> 尺子歪了就去修尺子，别拿刀去削文章，尤其别削招标文件规定要写的字。
